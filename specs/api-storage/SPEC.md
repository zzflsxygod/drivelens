## 1. Goal

DriveLens reads a user's TeslaMate database but must never change it. api-storage defines how that is guaranteed and where DriveLens keeps its own data: a login role `drivelens_ro` with read-only access to TeslaMate's `public` tables, and a separate schema `drivelens` that the API owns and upgrades by itself on every start. Because self-hosted installs differ (old manual SQL, missing privileges), each optional feature is switched off on its own when its tables are not usable, so the rest of the API keeps working and the operator gets a clear log line instead of a crash.

## 2. Responsibility boundaries

### 2.1 In scope
- `deploy/setup.sql`: role, grants, schema creation, ownership handover.
- The legacy SQL files in `deploy/` (`drivelens-init.sql`, `drivelens-v0.6.0.sql`, `drivelens-v0.6.1.sql`, `drivelens-v0.7.0.sql`, `drivelens-v0.16.0.sql`) and their relation to the current setup.
- The complete `drivelens` schema: every table, column, constraint, index and foreign key the API creates.
- The startup migration sequence (`migrate()` and each module's `try_migrate` / `try_create_tables`) and its idempotent, non-fatal behavior.
- The per-feature availability probes and their caching rules.
- What each endpoint group answers when its feature is unavailable (degradation matrix, 3.5).
- The TeslaMate tables the API depends on (read-only).
- Data lifecycle: cascade deletes, retention, uninstall.

### 2.2 Out of scope
- What the endpoints do with the data when the feature is available → `api-records`, `api-summary`, `api-insights`, `api-journeys`, `api-push`, `api-auth`.
- The startup log line format and `/api/health` response shape → `api-core` (this module supplies the probe results).
- Device-index loading, token hashing, expiry semantics → `api-auth` (this module only covers the `devices` / `pairing_codes` tables and availability).
- VAPID key generation and notifier state semantics → `api-push` (this module only covers the `push_state` / `push_subscriptions` tables).
- Deploying the database container, the compose file, running `setup.sql` in a pipeline → `ops-delivery`.

## 3. External behavior

### 3.1 Database account (`deploy/setup.sql`)
- **STOR-001** When `setup.sql` is run with `-v ro_pass=<password>` and the role `drivelens_ro` does not exist, the system SHALL create it as a `LOGIN` role with that password. (src: deploy/setup.sql:20-21)
- **STOR-002** When `setup.sql` is run again, the system SHALL set the password of `drivelens_ro` to `ro_pass`, and re-running SHALL be safe. (src: deploy/setup.sql:22; doc: docs/install.md "3. Create the database account (once)")
- **STOR-003** When `setup.sql` runs, the system SHALL grant `drivelens_ro` `CONNECT` on the current database, `USAGE` on schema `public`, `SELECT` on all existing tables in `public`, and default `SELECT` privileges on tables that the role running the script creates later in `public`. (src: deploy/setup.sql:24-28; doc: docs/install.md "3. Create the database account (once)")
- **STOR-004** When `setup.sql` runs, the system SHALL grant `REFERENCES` (not write access) on `public.cars`, `public.addresses`, `public.drives` and `public.charging_processes`. (src: deploy/setup.sql:29-31; doc: docs/install.md "3. Create the database account (once)")
- **STOR-005** When `setup.sql` runs, the system SHALL create schema `drivelens` with owner `drivelens_ro` if it does not exist, and SHALL grant `drivelens_ro` `USAGE` and `CREATE` on it also when it already exists. (src: deploy/setup.sql:33-34; doc: docs/install.md "3. Create the database account (once)")
- **STOR-006** When `setup.sql` runs and tables in schema `drivelens` are owned by another role, the system SHALL make `drivelens_ro` their owner, and SHALL change ownership of nothing outside schema `drivelens`. (src: deploy/setup.sql:35-38; doc: docs/install.md "Upgrading to 0.14.0")
- **STOR-007** When `setup.sql` runs, the system SHALL NOT create, alter or delete any object in TeslaMate's tables. (comment: deploy/setup.sql:8-9; doc: docs/install.md "3. Create the database account (once)")

### 3.2 Startup migration
- **STOR-010** When the API starts and schema `drivelens` does not exist, the system SHALL try `CREATE SCHEMA IF NOT EXISTS drivelens`; when that fails it SHALL log at ERROR level `schema drivelens does not exist and cannot be created (…); run deploy/setup.sql once as the TeslaMate DB admin (see docs/install.md). Read-only features still work.`, skip every further migration step, and continue starting. (src: api/src/main.rs:553, 562-567) — see CB-1 for the "read-only features still work" claim.
- **STOR-011** When `drivelens.address_aliases` does not exist, the system SHALL create it; when that fails it SHALL log at WARN level `place aliases disabled: cannot create drivelens.address_aliases (…); <setup hint>` and continue. (src: api/src/main.rs:569-577)
- **STOR-012** When `drivelens.charge_costs` does not exist, the system SHALL create it; when that fails it SHALL log at WARN level `manual charge costs disabled: …` and continue. (src: api/src/main.rs:578-588)
- **STOR-013** When `drivelens.dismissed_suggestions` does not exist, the system SHALL try to create it and SHALL ignore a failure without logging. (src: api/src/journey.rs:40-41)
- **STOR-014** When `drivelens.journey_drives` does not exist, the system SHALL run, in order, the DDL for `journeys`, `journey_drives` and `journey_drives_journey_id_idx`; on the first failure it SHALL log at WARN level `journeys disabled: cannot create tables (…); run deploy/setup.sql and restart the API` and stop this step. When `journey_drives` exists, the system SHALL skip this step. (src: api/src/journey.rs:42-49)
- **STOR-015** When `drivelens.journeys` exists and either column `journeys.cover_updated_at` or table `weather_hourly` is missing, the system SHALL add the columns `cover_image` and `cover_updated_at` (`ADD COLUMN IF NOT EXISTS`) and create `weather_hourly`; on the first failure it SHALL log at WARN level `journey cover / weather cache schema not applied (…)` and stop this step. When `journeys` does not exist, or both objects exist, it SHALL do nothing. (src: api/src/phase2.rs:23-29; comment: api/src/phase2.rs:21-22)
- **STOR-016** When `push_subscriptions` or `push_state` does not exist, the system SHALL run `CREATE TABLE IF NOT EXISTS` for both; on the first failure it SHALL log at WARN level `web push disabled: cannot create tables (…); <push hint>` and stop this step. (src: api/src/push.rs:45-50)
- **STOR-017** When `drivelens.devices` or `drivelens.pairing_codes` does not exist, the system SHALL create the missing table(s) in the order `devices`, `pairing_codes`; on a failure it SHALL log at WARN level `device auth disabled: cannot create <table> (…); <fix>. Everything else keeps working with the owner key (API_TOKEN).` and skip the rest of this step. (src: api/src/auth.rs:78-85; doc: CHANGELOG.md v1.2.0 "Database")
- **STOR-018** When `push_subscriptions` exists without column `device_id`, the system SHALL add `device_id bigint REFERENCES drivelens.devices(id) ON DELETE CASCADE`; when that fails it SHALL log a warning that notifications keep working but are not removed with a revoked device. When `push_subscriptions` does not exist, it SHALL log a warning that push subscriptions will not be linked to devices. (src: api/src/auth.rs:86-93)
- **STOR-019** When the migration runs, the steps SHALL execute in the order: schema, `address_aliases`, `charge_costs`, journeys and dismissal (`journey::try_create_tables`), cover/weather (`phase2::try_migrate`), push (`push::try_migrate`), device auth (`auth::try_migrate`). Device auth runs after push so it can link subscriptions to devices. (src: api/src/main.rs:562-592; comment: api/src/main.rs:592)
- **STOR-020** When the migration runs against a database where every object already exists, the system SHALL change nothing and complete successfully; running it twice in a row SHALL succeed. (test: api/src/main.rs auth_tests::db_device_flow; comment: api/src/main.rs:555-558; doc: CHANGELOG.md header "The API upgrades its own `drivelens` schema on start")
- **STOR-021** When an object already exists, the system SHALL detect it before issuing DDL, so a role without `CREATE` on the schema does not attempt the DDL for that object. (comment: api/src/main.rs:557-558; comment: api/src/auth.rs:76-77; comment: api/src/phase2.rs:21-22; src: api/src/main.rs:569-570, 578-579)
- **STOR-022** When a migration step fails because of missing privileges, the system SHALL continue starting and SHALL disable only the affected feature. (comment: api/src/main.rs:555-558; doc: CHANGELOG.md v0.10.0; doc: docs/DEVELOPMENT.md "Database rules")
- **STOR-023** When the migration or any request handler writes data, the system SHALL write only to objects in schema `drivelens`; every `INSERT`, `UPDATE`, `DELETE`, `CREATE` and `ALTER` statement in `api/src/*.rs` targets `drivelens.*`. (src: api/src/main.rs:497-500, 507, 537-542, 548, 564; src: api/src/journey.rs:9-25; src: api/src/phase2.rs:11-19, 66, 73, 136-138; src: api/src/push.rs:21-43, 94; src: api/src/auth.rs:46-65; doc: README.md "How it works"; doc: CONTRIBUTING.md "Ground rules")

### 3.3 Feature availability probes
- **STOR-030** When the manual-costs probe (`costs_ok`) runs, the system SHALL report the feature available only if `drivelens.charge_costs` exists and `drivelens_ro` has `SELECT, INSERT, UPDATE, DELETE` on it. (src: api/src/main.rs:57-65)
- **STOR-031** When the journeys probe (`journey::tables_ok`) runs, the system SHALL report the feature available only if `journeys` and `journey_drives` exist, the role has `SELECT, INSERT, UPDATE, DELETE` on both, and `USAGE` on `journeys_id_seq`; a database error during the probe SHALL count as unavailable. (src: api/src/journey.rs:52-63)
- **STOR-032** When the suggestion-dismissal probe (`journey::dismiss_ok`) runs, the system SHALL report the feature available only if `dismissed_suggestions` exists and the role has `SELECT, INSERT, DELETE` on it. (src: api/src/journey.rs:28-37)
- **STOR-033** When the journey-cover probe (`phase2::cover_ok`) runs, the system SHALL report the feature available only if column `drivelens.journeys.cover_image` exists. (src: api/src/phase2.rs:31-37)
- **STOR-034** When the weather-cache probe (`phase2::weather_ok`) runs, the system SHALL report the feature available only if `weather_hourly` exists and the role has `SELECT, INSERT, UPDATE` on it. (src: api/src/phase2.rs:38-45)
- **STOR-035** When the web-push probe (`push::push_ok`) runs, the system SHALL report the feature available only if `push_subscriptions` and `push_state` exist, the role has `SELECT, INSERT, UPDATE, DELETE` on both and `USAGE` on `push_subscriptions_id_seq`. (src: api/src/push.rs:52-62)
- **STOR-036** When the device-auth probe runs, the system SHALL report the feature available only if `devices` and `pairing_codes` exist, the role has `SELECT, INSERT, UPDATE, DELETE` on both and `USAGE` on `devices_id_seq` and `pairing_codes_id_seq`. (src: api/src/auth.rs:96-103)
- **STOR-037** When one of the probes `costs_ok`, `journey::tables_ok`, `journey::dismiss_ok`, `phase2::cover_ok`, `phase2::weather_ok` or `push::push_ok` has returned `true`, the system SHALL keep returning `true` without querying until the process restarts; while it returns `false`, it SHALL query the database again on every use. (src: api/src/main.rs:40, 59, 63; src: api/src/journey.rs:30, 35, 54, 61; src: api/src/phase2.rs:32, 35, 39, 43; src: api/src/push.rs:53, 60; comment: api/src/main.rs:40, 55-56)
- **STOR-038** When an operator makes a missing feature usable while the API runs (for example by running SQL as the admin), the system SHALL pick it up on the next probe without a restart; for web push the notifier re-checks every 60 seconds. (comment: api/src/main.rs:55-56; src: api/src/push.rs:10, 13, 242)
- **STOR-039** When device-auth availability is evaluated (at startup and every 300 seconds), the system SHALL switch the feature on when the probe passes and off when it fails, clearing the in-memory device list when it goes off; this probe is not latched. (src: api/src/auth.rs:34, 321-334, 343-372, 441-447)
- **STOR-040** When the startup feature log is written, the system SHALL report `teslamate read` as available only if `public.drives` exists and is selectable, and `place aliases` only if `drivelens.address_aliases` exists with `SELECT, INSERT, UPDATE, DELETE`. Place aliases have no other runtime probe. (src: api/src/main.rs:598-603)

### 3.4 TeslaMate data dependency
- **STOR-050** When the API reads vehicle data, it SHALL read only the TeslaMate tables `cars`, `drives`, `charging_processes`, `charges`, `positions`, `addresses`, `geofences`, `states` and `updates`, and the PostgreSQL catalogs. (src: api/src/main.rs:291-295, 366, 396, 423-432, 617; src: api/src/summary.rs:129, 147; src: api/src/insights.rs:162; src: testdata/schema.sql:2-52) Writes are covered by STOR-023.
- **STOR-051** When a TeslaMate row referenced by a DriveLens row is deleted (`addresses`, `charging_processes`, `cars`, `drives`), the database SHALL delete the referencing DriveLens rows (`address_aliases`, `charge_costs`, `journeys` and their `journey_drives`, `journey_drives`, `dismissed_suggestions`). (src: api/src/main.rs:573, 582; src: api/src/journey.rs:12, 18-19, 24; comment: deploy/setup.sql:29-30; doc: docs/install.md "3. Create the database account (once)")
- **STOR-052** When a device row is deleted, the database SHALL delete the pairing codes it created and the push subscriptions linked to it. (src: api/src/auth.rs:62, 64-65; doc: SECURITY.md "Revoking and signing out")

### 3.6 Legacy SQL files

## 4. Key design decisions

- **D-1 Read-only TeslaMate, separate schema.** DriveLens data lives only in `drivelens`; TeslaMate tables get `SELECT` (and `REFERENCES` for foreign keys). Rationale: TeslaMate's data must never be modified. (doc: README.md "How it works"; doc: CONTRIBUTING.md "Ground rules"; comment: deploy/setup.sql:8-9)
- **D-2 The API migrates its own schema.** One `setup.sql` creates the role and schema; the API creates and upgrades every table at startup. Rationale: "no manual SQL is needed after the one-time setup.sql". (doc: CHANGELOG.md header; doc: CHANGELOG.md v0.10.0; comment: deploy/setup.sql:10-13)
- **D-3 No migration framework.** Hand-written, existence-checked DDL instead of sqlx's migrator, because the migrator's bookkeeping table would need `CREATE` rights and would conflict with schemas created by the old SQL files. (comment: api/src/main.rs:559-560)
- **D-4 Degrade per feature, never crash.** Missing objects disable one feature with a log line naming the fix; read paths fall back (e.g. TeslaMate cost only) and write paths answer 503 with a remediation message. (comment: api/src/main.rs:555-558; comment: api/src/journey.rs:3; doc: docs/DEVELOPMENT.md "Database rules")
- **D-5 Latched probes.** Feature probes are cached once true and re-checked while false, so an operator can fix privileges without restarting while healthy installs pay no per-request catalog queries. (comment: api/src/main.rs:40, 55-56) Device auth is the exception: it is re-evaluated every 5 minutes in both directions, together with the device-index reload. (src: api/src/auth.rs:341-372, 440-447)
- **D-6 Ownership handover instead of grants per table.** `setup.sql` makes `drivelens_ro` the owner of the schema and of legacy tables, because `ALTER TABLE` (e.g. adding `push_subscriptions.device_id`) requires ownership even with `IF NOT EXISTS`. (comment: deploy/setup.sql:14-15, 35-36; comment: api/src/phase2.rs:21-22; doc: CHANGELOG.md v1.2.0 "Upgrade note")
- **D-7 Foreign keys with cascade into TeslaMate tables.** DriveLens rows reference TeslaMate rows so that "DriveLens data is cleaned up when TeslaMate deletes a drive / charge / car". (comment: deploy/setup.sql:29-30)
- **D-8 Weather cache on a 0.1° grid.** Weather is cached per rounded coordinate and hour, which also limits the precision sent to Open-Meteo to about 10 km. (comment: deploy/drivelens-v0.7.0.sql:10-13; doc: SECURITY.md "Privacy promise")
- **D-9 Secrets stored as hashes.** `devices.token_hash` and `pairing_codes.code_hash` are 32-byte SHA-256 values; raw tokens and codes are not stored. (src: api/src/auth.rs:49, 59; doc: SECURITY.md "Privacy promise")

## 5. Constraints

- `setup.sql` must run as the TeslaMate database admin through `psql` (it uses `\gexec` and the `ro_pass` variable). (comment: deploy/setup.sql:2-5)
- The default compose setup expects database `teslamate` and admin user `teslamate`; other names need `-U`/`-d` and `DRIVELENS_DB_NAME`. (doc: docs/install.md "3. Create the database account (once)")
- Device auth needs `CREATE` on schema `drivelens` and `drivelens_ro` ownership of the DriveLens tables. (doc: docs/install.md "Devices"; doc: docs/install.md "Upgrading to 0.14.0")
- Value limits enforced by the database: alias name non-blank; cost amount `numeric(12,2)` ≥ 0 with 3-letter upper-case currency; journey name non-blank; device name 1–60 characters after trim; scope `full` | `read`; `device_ttl_days` 1–365; push `locale` `zh` | `en` | `ja`. (src: api/src/main.rs:574, 583-584; src: api/src/journey.rs:13; src: api/src/auth.rs:48, 50, 60-61; src: api/src/push.rs:31)
- Probe results for latched features are not invalidated if an object is later dropped or a privilege revoked; recovery needs a restart. (src: api/src/main.rs:59, 63)
- Uninstalling removes all DriveLens data with `DROP SCHEMA drivelens CASCADE`, `DROP OWNED BY drivelens_ro`, `DROP ROLE drivelens_ro`; TeslaMate data is not touched. (doc: docs/install.md "Uninstall")

## 6. Non-goals

- Writing to, altering or adding indexes on TeslaMate's tables. (doc: README.md "How it works"; doc: CONTRIBUTING.md "Ground rules")
- Down-migrations or schema version bookkeeping. (comment: api/src/main.rs:559-560) Confirmed (owner decision): migrations are additive only (`CREATE … IF NOT EXISTS`); uninstalling is `DROP SCHEMA drivelens CASCADE`, so no down-migrations are kept.
- Pruning the weather cache: no code deletes rows from `weather_hourly`. Confirmed from code: the only write is the insert/upsert at api/src/phase2.rs:136-138; rows are small (one per 0.1° cell-hour actually viewed).
- Requiring the legacy `deploy/drivelens-*.sql` files on new installs. (comment: deploy/setup.sql:18)
